# LOVE connect HUB 規格 第1版

LOVE rhetoric の全アプリが、どんな種類のデータでも同じ作法で出し入れするための共通規格。
本書が正本で、`src/` の中核部品は本書のとおりに動く。食い違いがあれば本書に合わせて直す。

PLEATS. ハブ規格 第1版（土台とハブの分け方、窓口、権限の段階）は、本規格の上に乗る「業務のハブの作り方」として引き続き有効。本規格は、その下を流れるデータの通り道を決める。

---

## 1. 追求すること（優先順）

| 順 | 目標 | 本規格での意味 |
|---|---|---|
| 1 | 機密性 | 許可の書いていないものはすべて拒否する。秘密の値はレーンを流さない |
| 2 | レスポンス | 遅れると価値がなくなるものから先に通す。締め切りを過ぎたものはすぐ捨てる |
| 3 | 速度 | 本文を読む前に、見出し（封筒）だけで受け取るかどうかを決める |
| 4 | 軽さ | 実行時の外部部品はゼロ。標準機能（Web Crypto）だけで、Workers・Node.js・ブラウザで動く |

目標どうしがぶつかったときは、上の順を優先する（例：速度のために署名を省くことはしない）。

## 2. 用語

- **レーン**：データの流れ方ごとの通り道。8 本（第3章）。
- **形式**：レーンの中のデータの種類。`レーン名.分類.名前` の形（例：`media.image.webp`）。
- **封筒**：全レーン共通の入れ物。見出し（小さい）と本文（任意）からなる（第4章）。
- **土台**：封筒を受け取り、検査し、届ける側。時刻・鍵・保存先は土台だけが持つ。
- **機密度**：0 公開 ／ 1 社内 ／ 2 機密 ／ 3 極秘。

## 3. 8 本のレーン

優先度は小さいほど先に処理する。値は `src/lanes.ts` と同じ。

| 優先 | レーン | 流れるもの | 届け方 | 本文の直接持ち込み上限 | 締め切りの既定 | 保存の既定 | 必須の項目 | 機密度の下限 |
|---|---|---|---|---|---|---|---|---|
| 0 | `key` 鍵 | API キー・トークン・本人確認 | 一往復 | 禁止 | 2 秒 | 保存しない（変更不可） | `ref` | 3 |
| 1 | `stream` ストリーミング | 配信・録音・センサー・ログ | 連続（古いものは捨ててよい） | 16 KiB | 1 秒 | 保存しない | `sq` | 0 |
| 2 | `sync` 同期 | 共同編集・チャット・端末間の同期 | 双方向 | 64 KiB | 3 秒 | 30 日 | `sq` `bv` | 0 |
| 3 | `api` API | 外部サービスとのやり取り | 一往復 | 256 KiB | 10 秒 | 7 日 | なし | 0 |
| 4 | `ai` AI | 指示文・応答・逐次生成・ベクトル | 逐次 | 256 KiB | 120 秒 | 7 日 | なし | 1 |
| 5 | `record` レコード | 表のデータ（社員・案件・勤怠など） | 一往復 | 64 KiB | 5 秒 | 保存先に従う | なし | 1 |
| 6 | `event` イベント | 通知・Webhook・「〇〇が起きた」 | 一方向 | 16 KiB | なし | 7 日 | なし | 0 |
| 7 | `media` メディア | 画像・音声・動画・PDF などのファイル | 分割（1 片 1 MiB） | 禁止 | なし | 保存先に従う | `ref` `len` `h` | 0 |

### レーンごとの約束

- **鍵**：値そのものは決して運ばない。運ぶのは置き場所の参照（`ref`。例：LININGS. の鍵の番号）だけ。値は、使う瞬間に土台が置き場所から取り出し、通信に差し込む。
- **ストリーミング**：`sq`（順番）で並べ直す。締め切りを過ぎた片は待たずに捨てる。途中から受け取り始めてよい。
- **同期**：`bv`（元の版）を添えて書く。元の版が今の版と違えば、土台がまとめるか、書き手に差し戻す。
- **API**：同じ `id` の要求は一度だけ実行する（二重の支払い・二重の登録を防ぐ）。
- **AI**：逐次返る断片には `sq` を付ける。機密度は最低でも社内（1）。
- **レコード**：更新には `bv` を添える（PLEATS. の「版の確認」と同じ）。大量の取り込み・書き出しは、同じレーンで `sq` を付けて分割し、最後に件数とハッシュで照合する。
- **イベント**：同じ `id` は一度だけ処理する。重複して届くことを前提にする。
- **メディア**：本文は封筒に入れない。`ref`（置き場所）・`len`（大きさ）・`h`（SHA-256）を送り、受け手は受け取った中身を必ず `len` と `h` で照合してから使う。

### レーンにしないもの

新しい種類のデータは、レーンを増やさず、既存のレーンの**形式**として登録する。

| データ | 入れるレーン |
|---|---|
| 一括の取り込み・書き出し・移行 | レコード（分割して最後に照合） |
| 時間のかかる処理（動画変換など） | API で依頼し、イベントで完了を知らせる |
| 位置情報・計測値・機器（IoT） | ストリーミング、またはイベント |
| 3D・新しい画像や音声の形式 | メディア |
| 決済 | API（同じ `id` は一度だけ。承認 `ap` を付ける） |

## 4. 封筒

項目名は短くして、見出しを軽くする。ここに無い項目は拒否する。

| 項目 | 意味 | 必須 | 形 |
|---|---|---|---|
| `v` | 規格版 | 必須 | 今は `1` |
| `l` | レーン | 必須 | 第3章の 8 つのどれか |
| `f` | 形式 | 必須 | 小文字の英数字を `.` でつなぐ（2〜8 段） |
| `id` | 一意の番号 | 必須 | 英数字・`_`・`-` の 8〜64 字 |
| `co` | 会社 ID | 必須 | 英数字・`_`・`-` の 1〜64 字 |
| `by` | 送り手 | 必須 | 同上 |
| `at` | 時刻（ミリ秒） | 必須 | 土台が付ける。送り手は付けない |
| `c` | 機密度 | 必須 | 0〜3 |
| `dl` | 締め切り（`at` からのミリ秒） | 任意 | 0〜600000。0 は締め切りなし |
| `ap` | 承認が要る | 任意 | 真偽 |
| `ret` | 保存期間（秒） | 任意 | 0 は保存しない |
| `sq` | 順番 | レーンによる | 0 以上の整数 |
| `bv` | 元の版 | レーンによる | 0 以上の整数 |
| `ref` | 本文の置き場所 | レーンによる | 512 字まで |
| `len` | 本文の大きさ（バイト） | レーンによる | 0 以上の整数 |
| `h` | 本文の SHA-256 | レーンによる | 16 進の小文字 64 字 |
| `e` | 本文の暗号方式 | 極秘の本文は必須 | `A256GCM` |
| `b` | 本文 | 任意 | JSON の値。暗号化したときは文字列 |
| `sig` | 署名 | 機密以上は必須 | HMAC-SHA256 の base64url（43 字） |

- 本文（`b`）と置き場所（`ref`）は、どちらか一方だけ。
- 見出し（本文を除いた封筒）は 2 KiB まで。

## 5. 機密性の決まり

1. **許可の書いていないものは禁止**：規格に無い項目、規格に無いレーン、許可表に無い形式は、すべて拒否する。本番の土台は、ハブごとに許す形式の表を必ず渡す。
2. **鍵は流さない**：鍵レーンは本文を持てず、機密度は極秘、保存期間は 0 に固定。
3. **機密以上（2・3）は署名が必須**：署名は HMAC-SHA256。対象は `sig` を除く封筒全体（項目名を並べ替えた JSON）。どの項目を 1 文字変えても検査に通らない。署名は土台の送り口が `at` を付けた後に付ける。
4. **極秘（3）の本文は暗号化が必須**：AES-256-GCM。暗号文は「会社 ID ＋ 一意の番号」に結び付け、別の封筒に付け替えると開けない。
5. **記録には本文を残さない**：社内以上（1〜3）の封筒を記録に残すときは、本文と署名を外し、大きさだけを残す（`redact`）。
6. **鍵の値は土台だけが持つ**：署名用・暗号化用の鍵は、鍵レーンを通して土台が取り出す。ハブ・リポジトリ・記録・チャットに値を書かない。

## 6. レスポンスと速度の決まり

1. **検査は安い順**：受け口は、まず受け取った全体の長さで上限を確かめ、次に見出しを検査し、本文には最後にだけ触る。
2. **締め切り**：`at + dl`（無ければレーンの既定）を過ぎた封筒は、処理せずに捨てる。時刻は土台の時計だけを使う。
3. **処理の順番**：混み合ったときは、レーンの優先度 → 締め切りの早いもの → 古いもの、の順に処理する（`compareUrgency`）。
4. **大きいものは置き場所で渡す**：本文が上限を超えるときは、封筒に入れずに `ref` で渡す。メディアは 1 MiB ずつに分けて送る。
5. **重複は入口で弾く**：同じ会社・同じ `id` は、決めた時間のあいだ一度だけ通す（`createDedupe`）。記憶の量には上限を設ける。

参考の実測（Node.js 22）：封筒の検査は 1 件あたり約 3 マイクロ秒、署名の確認は約 70 マイクロ秒。

## 7. 軽さの決まり

1. 中核部品の実行時の外部部品はゼロ。開発用（型検査）の部品だけを使う。
2. 標準機能（`crypto.subtle`・`TextEncoder`・`btoa`）だけで書き、Cloudflare Workers・Node.js 22.6 以上・ブラウザで同じように動かす。
3. 封筒の項目名は 1〜3 字に縮める。

## 8. 全レーン共通の性質

レーンではなく、どのレーンの封筒にも付く性質として扱う。

| 性質 | 項目 | 決まり |
|---|---|---|
| 機密度 | `c` | 第5章 |
| 承認 | `ap` | `true` の封筒は、人が承認するまで実行しない（準備 → 承認 → 実行）。承認は利用者本人が行い、AI は代わりに承認しない |
| 保存期間 | `ret` | 過ぎたら消す。鍵は常に 0 |
| 記録 | — | 誰が・いつ・何をしたかを土台が必ず残す。本文は第5章の 5 に従う |

## 9. 中核部品（`src/`）

| 部品 | 中身 |
|---|---|
| `lanes.ts` | 8 本のレーンの定義（第3章の表） |
| `envelope.ts` | 封筒の検査 `checkEnvelope`、締め切り `isExpired`、保存期間 `retentionOf`、記録用 `redact` |
| `crypto.ts` | 署名 `signEnvelope`・`verifyEnvelope`、暗号化 `sealBody`・`openBody`、ハッシュ `sha256Hex`・`matchesBody` |
| `dedupe.ts` | 重複防止 `createDedupe` |
| `index.ts` | 入口と処理の順番 `compareUrgency` |

検査に通らなかったときは、`code`（機械向けの決まった名前）・`field`（どの項目か）・`message`（日本語の説明）を返す。

## 10. 版の決まり

- レーンの追加・削除、項目の追加・意味の変更、上限や既定値の変更は、規格版（`v`）を上げる変更とする。
- 土台は対応する版の範囲を持ち、範囲外の封筒は拒否する。古い版のハブは古い版のまま動く。
- 形式の追加は版を上げずに行える（許可表に足すだけ）。

## 11. 第1版で決めないこと

- 各レーンの通信の方式（HTTP・WebSocket など）の細部。封筒の約束だけを決めてある。
- 同期レーンで、ぶつかった変更をまとめる具体的な方法。
- 鍵の置き場所（LININGS. など）との具体的なつなぎ方。

## 12. 次の作業

1. 各レーンの送り口・受け口を、この中核部品の上に作る（優先：鍵 → レコード → イベント → メディア）。
2. PLEATS.（N.S Connection）・LININGS.・Upbeater・LIFElive のやり取りを、封筒の形に当てはめて足りない点を洗い出す。
3. 形式の許可表の書き方（ハブの定義書のどこに書くか）を決める。
