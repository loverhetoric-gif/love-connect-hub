# LOVE connect HUB 第2版 計画（2026-11-14 調査）

本番の業務で使える水準にするため、2026年11月時点で標準化・提供済みの技術から、採用するものを決めた。
優先は規格書第1章どおり「機密性 → レスポンス → 速度 → 軽さ」。採用するのは、標準（RFC・FIPS）か、提供元が本番向けと明言しているものだけ。

## A. 本番の前に必ず入れる

| 穴 | 採用する技術 | 理由 |
|---|---|---|
| 二重実行を台数をまたいで防げない | **Cloudflare Durable Objects（SQLite 型）** を、会社ごと（必要なら会社＋利用者ごと）に 1 つ置き、受け取り済みの番号を保存する | 名前ごとに 1 か所でしか動かず、1 件ずつ処理するため、取り合いが起きない。SQLite は 2025 年 4 月に正式版・1 つ 10 GB |
|  | → 2026-11-18：`adapters/cloudflare/dedupe.ts`（1.9.0）として入れた。受け口・利用者の口・端末の確認の使い捨ての番号に渡せる。中身の指紋（下の行）は次に入れる |  |
| 利用者ごとの回数制限が無い | **Workers の Rate Limiting バインディング**（2025 年 9 月に本番向けとして安定版）で、利用者 ID ごとに制限。厳密さが要る操作だけ Durable Objects で数える | 速い。ただし数えるのは Cloudflare の拠点ごとなので、厳密な上限は Durable Objects に任せる |
| 「誰が・いつ・何をしたか」の記録が無い | **ハッシュの鎖でつないだ追記専用の記録**（各行に前の行の SHA-256 を持たせる）。会社ごとに鎖を分け、一定時間ごとに鎖の先頭のハッシュを外部（R2 の上書き不可の置き場所など）に写す | 書き換え・削除・差し込みが必ず見つかる。外部に写すことで、管理者でも隠せなくなる。派遣法・監査の証拠として出せる |
| 同じ番号で別の中身を送られたとき | 番号に加えて**中身のハッシュ（指紋）**も保存し、同じ番号で中身が違えば 422 で断る（IETF の Idempotency-Key の案と同じ扱い） | 誤りや悪意の送り直しで、別の処理が通るのを防ぐ |

## B. アプリを盗用・改造から守る（ネイティブアプリの公開前に入れる）

| 脅威 | 採用する技術 | 理由 |
|---|---|---|
| トークンが盗まれて別の端末で使われる | **DPoP（RFC 9449）**：端末の中で作った鍵（iPhone は Secure Enclave、Android は Keystore/StrongBox。取り出せない）で、送るたびに証明を付ける。トークンはその鍵に結び付ける | 持っているだけでは使えないトークンになる。OAuth 2.1 と MCP も推奨している |
|  | → 2026-11-18：端末の鍵（規格書 第21章、1.8.0）として入れた。WARPHOLE. の取り出せない鍵・ペアリング・Face ID の承認を元にした。残りは、実行をまたぐ使い捨ての番号の記憶（A の Durable Objects）と Kotlin 版 |  |
| 改造したアプリ・偽のアプリからの送信 | **iPhone：App Attest**（Apple が本物のアプリと端末を証明）、**Android：Play Integrity API の standard 要求**（送る内容のハッシュを結び付ける） | 本物のアプリからの送信だけを受け付けられる。確かめるのはサーバーだけ |
|  | → 2026-11-18：登録のときの確認として入れた。Android は鍵の証明書（1.10.0）、iPhone・iPad・Mac は App Attest（1.11.0）。残りは、送るたびの確認（App Attest の assertion・Play Integrity） |  |

## C. 先を見て入れる（量子計算機への備え）

| 対象 | 採用する技術 | 時期 |
|---|---|---|
| 署名 | **ML-DSA（FIPS 204）** を、今の HMAC・ECDSA と並べて使える形にする（規格版を上げる） | Cloudflare Workers は 2026 年 10 月 1 日から Web Crypto で ML-DSA・ML-KEM に対応（`webcrypto_modern_algorithms` の指定が必要）。仕様は草案なので、まずは任意で使える形にとどめる |
| 極秘の本文の暗号化 | **ML-KEM-768（FIPS 203）＋ HPKE** | 同上。ブラウザ（Chrome）はまだ試験段階のため、土台どうしの通信から始める |

## D. 品質を保つ仕組み

1. Upbeater で、PR ごとに `npm run check`・`swift test`・相互の確認を自動で走らせる。
2. 受け口・下書き・トークン・記録に、ランダムな入力を大量に当てる試験（ファジング）を足す。
3. Kotlin 版（Android）を、Swift 版と同じ試験と相互の確認で作る。
4. 第三者の点検（脆弱性診断）を、本番の前に一度受ける。

## 進める順

1. A（二重実行・回数制限・記録・中身の指紋）と D-1（自動検査）
2. N.S Connection の打刻だけを LOVE connect HUB 経由にして、本番で試す
3. B（DPoP・App Attest・Play Integrity）と D-3（Kotlin 版）→ ネイティブアプリの公開
4. C（量子計算機への備え）、D-2・D-4

## 中核部品と Cloudflare の分け方

作業規約どおり、`src/` には特定の公開先に依存する処理を書かない。
`src/` には「重複の記録」「回数制限」「記録の書き込み」の**形（インターフェース）**だけを置き、Cloudflare（Durable Objects・Rate Limiting・R2）で動かす部品は `adapters/cloudflare/` に分ける。
